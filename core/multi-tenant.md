# 多租戶與組織

平台的「租戶」就是**組織(`Organization`)**。每個使用者屬於一個組織,每筆業務資料帶一個 `OrgId`,平台**自動**讓你只看到、只能寫到自己組織的資料——這層隱形過濾的機制在 [data-pipes](data-pipes.md),這篇不重講。

這篇回答的是**從 code 看不出來的那兩件事**:組織之間怎麼連成一張圖,以及「跨組織存取別人的資料」到底能到多遠——而那個範圍**讀和寫不一樣**。

---

## 三層歸屬

```
Organization(租戶)
  └─ PlatformGroup(群組,掛角色)
       └─ PlatformUser(使用者)
```

- **使用者**靠 `OrgId` 綁在某個組織下;`Account` 不是全域唯一,**(帳號 × 組織)才是**——同一組帳號可在多個組織各自存在(見 [login](login.md) 的登入消歧)。
- **角色掛在群組上**,不直接掛人;使用者透過群組成員身分取得角色。角色樹本身見 [權限 / 角色樹](permissions.md)。
- **組織** 是最外層的租戶邊界,也是 `OrgId` 自動過濾的依據。

三個容易誤解的旗標:

| 旗標 | 在哪 | 意思 |
|---|---|---|
| `IsOrgAdmin` | `PlatformUser` | 該組織的管理員。**列使用者時看不到同組織的其他 admin、也看不到自己**(防互改 / 防越權,見下方 gotcha)。 |
| `IsOrgRootGroup` | `PlatformGroup` | 組織建立時自動產生的根群組(管理員群組),**受保護、不出現在一般群組清單**。 |
| `IsSystemData` | `PlatformUser` | 系統 / 代理用使用者(如 Proxy 登入產生的),**預設被濾掉**,不出現在一般使用者清單。 |

---

## 組織關係:一棵樹(單一父組織)

組織之間是**父子階層**,而且是一棵**樹**:每個組織只有一個父組織,樹根是平台啟動時建立的**預設(super)組織**。新建組織預設掛在建立者的組織底下。

```
        ┌─────────┐
        │  總公司  │   ← 預設(super)組織,樹根
        └────┬────┘
       ┌─────┴─────┐
   ┌───▼──┐    ┌──▼───┐
   │ 分店A │    │ 分店B │
   └──────┘    └──────┘
```

父子邊存在 **`AuthorizedOrganization`** 關聯表(`Organization` 自我參照)。這只是「自我參照階層」在關聯式 DB 的標準存法——關聯表結構上**容得下**一個組織掛多個父,但**那不是平台支援的結構,只是表示法的副作用**:標準管理 UI 只建單父(「加子組織」的候選清單會排除已經有父的組織),語意上也只當樹處理。**別把這張多對多表當成「支援多父圖」**;硬去直寫關聯表造出多父,平台資料層擋不住,但沒有任何介面或行為保證它會正常運作。

其他兩個不直覺性質:

- **只算啟用中的組織**:`Organization.ChildOrganizations` / `ParentOrganizations` 都**只回 `IsActived == true` 的鄰居**。**停用一個組織,它就從父 / 子清單上消失**——連帶下面講的跨組織可達性也跟著斷掉。
- **只有一層,不遞迴**:`ChildOrganizations` 是**直接子組織**,不是整棵子樹。總公司能跨到分店,但**跨不到分店底下的櫃位**——孫層要再給一條直接邊,或由分店自己處理。

---

## 跨組織資料存取:讀能上下、寫只能往下

預設每個人**只看 / 只寫自己組織**(`OrgId == 我的組織`)。要讓某些角色「跨組織」存取,用 `AllowChildOrganizationData(role)` 把這個能力綁在一個角色字串上(底層是放寬該請求的 `OrganizationDataFilterSetting`,見 [data-pipes](data-pipes.md))。

**但讀和寫的可及範圍刻意不對稱**,這是這篇最重要的一點:

| | 預設(表單不帶 `OrgId`) | 開了跨組織授權 + UI 把 `OrgId` 拉出來讓你選 |
|---|---|---|
| **讀** | 只看自己組織 | 可往**下**看直接子組織(`AllowChildOrganizationData`)、也可往**上**看父組織(`AllowParentsData`)——**兩個旗標各自獨立**,要哪個給哪個 |
| **寫** | 寫進自己組織;沒帶 `OrgId`(或帶 0)一律蓋成自己的,更新時 `OrgId` 鎖住搬不走 | 可寫到**自己或直接子組織**——挑你指定的那個;**挑了範圍外(含父組織)→ 退回自己組織** |

寫跨組織**不是自動的,要兩個條件同時成立**:(1) 角色開了 `AllowChildOrganizationData`,(2) **UI 真的把 `OrgId` 欄位「拉出來」**、表單帶了一個目標 `OrgId`。少任何一個——沒開授權、表單沒帶 `OrgId`(=0)、或帶的 `OrgId` 不在可寫範圍——平台就把它**蓋回 / 鎖回你自己的組織**。所以平常表單沒拉 `OrgId`,感覺就是「只能寫自己」。

可寫範圍綁在 `IUserOrganization.AllOrganizations`,定義是 **`自己 + 直接子組織`**(不含父組織)。所以即使你**讀**得到父組織的資料(開了 `AllowParentsData`),挑父組織當寫入目標也會被退回——**寫永遠回不到上層**。

> 一句話記:**看得到上層 ≠ 改得動上層。** 跨組織的「寫」是單向往下的;往上只能看。

`IUserOrganization` 是每個請求當場解析出來的組織脈絡(自己的組織、`OrgKey`、父清單、子清單、可寫的 `AllOrganizations`),登入時就備好,後續所有過濾都讀它。

## Gotchas 一覽

- **看得到不代表改得動**:開了 `AllowParentsData` 能讀父組織資料,但寫入永遠回不到父層——`OrgId` 會被鎖。要往上寫是設計上不允許的。
- **跨組織只有一層**:`AllowChildOrganizationData` 只到**直接**子組織,不是整棵子樹。要跨到孫層得補直接的授權邊。
- **停用組織 = 從圖上消失**:`IsActived = false` 的組織不再出現在任何人的父 / 子清單,跨組織可達性立刻中斷;不是刪除,但效果上「斷線」。
- **繞過 `ITable` / 直接用 `DbContext` = 繞過租戶過濾**:跟 [data-pipes](data-pipes.md) 同一個 footgun——直接 `dbContext.Set<T>()` 不會套 `OrgId` 過濾,跨租戶資料會整碗端出。要過濾就走 `ITable` / entity-api。
- **改不了同組織的其他管理員、也改不了自己**:列使用者時平台自動把「同組織的其他 `IsOrgAdmin`」和「自己」濾掉,避免管理員互改或自我提權。
- **管不了權力比你大的群組,也看不到自己的群組**:列群組時(同組織內)會濾掉根群組、**你自己已加入的群組**、以及「角色不是你全都有」的群組——防止用低權帳號去改高權群組或自我提權。其他組織的群組由前面的跨組織過濾決定能否看到,不歸這條。
